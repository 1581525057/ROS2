从“接不接”
升级到“停不停”

保留第一版的 GoalResponse，再增加 CancelResponse。客户端按 Ctrl+C 会发送取消请求，服务端允许后安全结束正在执行的任务。

范围确认

第二次升级的边界

新增能力

cancel_callback 决定是否允许取消；执行循环发现请求后调用 canceled()。

客户端配合

保存 GoalHandle，把客户端终端的 Ctrl+C 转换成 cancel_goal_async()。

升级前

原来：Goal 来了就直接执行

原来的 ActionServer 只登记执行回调。无论地点是不是空字符串、步数是不是 0，服务端都没有一个专门的入口提前判断。

原来的核心写法
# chapt5_ws/src/patrol_action/patrol_action/patrol_server.py
self.patrol_action_server = ActionServer(
    self, Patrol, 'patrol', self.handle_patrol_action_server
)
为什么升级：如果 Goal 本身就不合法，最好在任务开始前拒绝，而不是进入执行回调后再处理。
第 1 小步

导入 GoalResponse

它是服务端给“是否接单”这个问题的标准答案类型。

新增一行导入
# chapt5_ws/src/patrol_action/patrol_action/patrol_server.py
from rclpy.action import ActionServer
from rclpy.action import GoalResponse
返回值意思后续
GoalResponse.ACCEPT接受目标继续进入执行回调
GoalResponse.REJECT拒绝目标任务不会开始
第 2 小步

写一个快速检查回调

goal_request 就是客户端发送的 Patrol.Goal。这里只检查，不执行巡逻。

检查地点和步数
# chapt5_ws/src/patrol_action/patrol_action/patrol_server.py
def goal_callback(self, goal_request: Patrol.Goal) -> GoalResponse:
    if not goal_request.target_name.strip():
        return GoalResponse.REJECT

    if not 1 <= goal_request.total_steps <= 100:
        return GoalResponse.REJECT

    return GoalResponse.ACCEPT
strip() 的作用：去掉字符串两边空格，所以 " " 也会被当成空地点。
检查规则：地点不能为空；步数只能是 1 到 100，包含 1 和 100。
第 3 小步

把回调注册给 ActionServer

只定义函数还不够。必须通过 goal_callback=... 告诉服务端，新 Goal 到达时要调用谁。

唯一需要加入 ActionServer 的参数
# chapt5_ws/src/patrol_action/patrol_action/patrol_server.py
self.patrol_action_server = ActionServer(
    self, Patrol, 'patrol', self.handle_patrol_action_server,
    goal_callback=self.goal_callback
)
最容易漏的地方：如果忘记注册，goal_callback 虽然写在文件里，却永远不会被调用。
执行顺序

Goal 现在有两条路

一句话：goal_callback 决定“执行回调有没有机会开始”。
第二次升级

CancelResponse：决定是否允许取消

取消像执行中的“撤单申请”。客户端不能直接停止服务端，只能提出请求；服务端返回 ACCEPT 或 REJECT。

第 1 步：注册取消回调

导入、注册、返回 ACCEPT
# chapt5_ws/src/patrol_action/patrol_action/patrol_server.py
from rclpy.action import ActionServer, CancelResponse

self.patrol_action_server = ActionServer(
    self, Patrol, 'patrol', self.handle_patrol_action_server,
    goal_callback=self.goal_callback,
    cancel_callback=self.cancel_callback,
    callback_group=self.callback_group
)

def cancel_callback(self, goal_handle) -> CancelResponse:
    self.get_logger().info('收到取消请求，允许取消任务')
    return CancelResponse.ACCEPT
只返回 ACCEPT 还不够：它只表示“同意撤单”。执行循环还必须检查请求并真正停止。

第 2 步：在循环的安全位置停止

每一步开始前检查取消
# chapt5_ws/src/patrol_action/patrol_action/patrol_server.py
for step in range(1, request.total_steps + 1):
    if goal_handle.is_cancel_requested:
        goal_handle.canceled()
        result = Patrol.Result()
        result.success = False
        result.message = '巡逻任务已取消'
        return result

    # 原来的 Feedback 代码继续执行

goal_handle.canceled() 设置 Action 的最终状态；result 则携带你定义的业务数据。这两件事都要做。

第 3 步：让执行与取消可以同时被处理

取消功能所需的并发支撑
# chapt5_ws/src/patrol_action/patrol_action/patrol_server.py
self.callback_group = ReentrantCallbackGroup()
# ActionServer 中加入 callback_group=self.callback_group

executor = MultiThreadedExecutor(num_threads=2)
executor.add_node(node)
executor.spin()

线程 1

运行巡逻循环，持续发布 Feedback。

线程 2

及时处理客户端发来的取消请求。

记忆：cancel_callback 决定“让不让停”，is_cancel_requested 决定“什么时候安全停”。

第 4 步：客户端把 Ctrl+C 变成取消请求

客户端保存 GoalHandle 并异步取消
# chapt5_ws/src/patrol_action/patrol_action/patrol_client.py
self.goal_handle = future.result()

def request_cancel(self):
    self.cancel_requested = True

def check_cancel_request(self):
    if self.cancel_requested and not self.cancel_sent:
        self.cancel_sent = True
        future = self.goal_handle.cancel_goal_async()
        future.add_done_callback(self.cancel_response)

Python 的 SIGINT 回调只设置布尔标志，ROS 定时器再调用取消 API。这样不会在系统信号处理函数中直接操作 ROS 实体。

总结

现在掌握了 Action 的两个决定

  1. GoalResponse：任务开始前，决定接不接。
  2. CancelResponse：任务执行中，决定是否允许取消。
  3. goal_handle.canceled()：确认任务已经安全停止。
仍然没有改：Patrol.action 接口、客户端参数和 action_msgs 依赖。

小练习：把 cancel_callback 临时改成 CancelResponse.REJECT，重新构建后再按 Ctrl+C，观察取消请求被拒绝。
